# 人類一鍵訂餐流程 PRD

## 目標

新增 `dtri-office-lunch order`，讓人類使用者以一個互動式指令完成現有的
`login → menu → prepare → submit` 流程。既有細粒度指令必須保留，供 Agent、
除錯與進階使用者使用。

## 使用流程

1. 執行 `dtri-office-lunch order`。
2. 若目前沒有有效登入，開啟可見瀏覽器並等待使用者手動完成登入、OTP 或 CAPTCHA；
   驗證成功後流程繼續。
3. 讀取並以既有短編號格式顯示當日菜單，提示使用者輸入一個餐點編號與可選備註。
4. 執行既有 `prepare` 邏輯，重新讀取菜單並建立一次性 `ORDER_TOKEN`。
5. 顯示完整訂單摘要（店家、品項、價格、數量固定為 1、備註），提示使用者輸入
   **精確大寫** `YES`。
6. 僅在收到 `YES` 後，呼叫既有 `submit` 邏輯；顯示成功、拒絕或不確定結果與下一步。

## 安全與例外處理

- 使用專案本機既有的 `browser-profile/` 作為持久瀏覽器設定檔，讓有效登入
  session 可供後續執行重用，避免使用者每次重新填寫登入表單。
- CLI／Playwright 不得讀取、列印、匯出、上傳或傳送 profile 內的帳號、密碼、OTP、
  CAPTCHA、Cookie 或 session 狀態；`browser-profile/` 不得提交至版本控制。
- 空白、取消、EOF、`YES` 以外的輸入：結束流程，不送出訂單。
- `ORDER_CHANGED`：不送出；顯示原因並回到菜單選擇。
- 登入失效：提示使用者完成登入後再繼續；不得偽造登入成功。
- `SUBMISSION_UNCERTAIN`：明確標示結果不確定，禁止在同次流程或重試指令中自動重送。
- 已送出或已嘗試送出的 token 不可再次使用。

## CLI 介面

```powershell
dtri-office-lunch order
```

本期不增加自動確認旗標，例如 `--yes`；不可用管線或預先提供的輸入跳過人類閱讀摘要與
輸入 `YES` 的關卡。

## 驗收條件

- 有效登入時，使用者只需執行一條指令、選擇餐點、輸入備註（可略過）及輸入 `YES`。
- 未登入時，流程在人工登入完成後從同一指令繼續，不要求使用者手動改跑 `menu` 或 `prepare`。
- 各安全例外都不會發出未經確認或重複的訂單 POST。
- `login`、`menu`、`prepare`、`submit` 的現有公開行為與 Agent Skill 不變。

## 非目標

- 多品項／購物車、數量大於 1、排程訂餐、背景自動下單。
- 改變網站登入機制或繞過 OTP、CAPTCHA。
- 自動重送任何已進入不確定狀態的訂單。
